# 中小 2D 游戏开发 · 4 个预设 Agent

一套可直接使用的「AI 小团队」预设。对应真实团队 **1 策划 + 2 客户端 + 2 美术 + 1 测试运营兼职** 的 5 人配置，压缩成 **4 个 Agent**：

| # | 预设 | 文件 | 一句话定位 | 内置双模式 |
| --- | --- | --- | --- | --- |
| 01 | 主策划（游戏设计师 / 制作人） | [01-主策划.md](01-主策划.md) | 把「好玩」翻译成可执行规格与表格 | – |
| 02 | 客户端程序 | [02-客户端程序.md](02-客户端程序.md) | 让「眼睛觉得对了」和「系统判对了」一致 | A 核心玩法/物理/判定 ↔ B UI/社交/商业化/适配 |
| 03 | 2D 美术 | [03-2D美术.md](03-2D美术.md) | 用最少资源把关键信息塞进玩家眼睛 | 原画/UI ↔ 动画/特效/资源优化 |
| 04 | 测试 / 运营（兼职） | [04-测试运营.md](04-测试运营.md) | 决定能不能发、发出去好不好 | – |

> 为什么是 4 个而不是 5 个：程序与美术各由 1 人分饰原 2 人的角色，用「模式切换」代替拆人；策划和测试运营本来就是单点。
> 每个文件都包含：身份与使命 → 职责边界 → 具体规格/模板 → 交付物 → 自检清单 → 与其他角色的接口 → 项目语境 → 可直接复制的启动语。

## 一、三种用法

### 用法 A：单会话角色扮演（最简单）

1. 开一个新对话；
2. 把对应文件**整份**粘贴为系统提示词（或首条消息）；
3. 再发一次文末的「启动语」，然后提需求。

可删掉文件首部的 `---` 元信息块，不影响使用。

### 用法 B：团队模式（推荐，多个 Agent 并行）

用支持多智能体协作的客户端（如 DeepSeek Harness 的 Agent Teams）：

1. **Lead** 使用 `01-主策划.md`（它负责拆任务、拍板、验收）；
2. 生成 3 个队友，分别给「02 / 03 / 04」的角色卡；
3. 每个队友的初始任务 = **角色卡摘要 + 启动语 + 本次具体任务 + 交付格式**，四样缺一不可。

建议给队友的任务消息模板：

```
【角色】客户端程序（A 模式）
【本次任务】实现第 3 关的判定与结算
【输入】docs/关卡表.csv 第 3 行；判定口径 = IoU（已确认）
【产出】可运行 Demo + 判定单测 + 一页技术说明
【约束】不改数值口径；所有参数来自配置表；单次判定 ≤0.2ms
【验收】测试用 10,000 次模拟，各评级占比落在策划目标区间
【截止】本迭代第 3 天
```

### 用法 C：写进项目里（长期生效）

把文件放到仓库如 `agents/` 或 `docs/agents/`，在项目说明（`AGENTS.md` / `CLAUDE.md` / `.cursor/rules`）里写一句：

> 做设计类工作前先读 `agents/01-主策划.md`；改客户端代码前先读 `agents/02-客户端程序.md`；依此类推。

这样任何会话、任何工具都能读到同一套角色约定，避免「每次都要重新交代背景」。

## 二、推荐协作流程（5 个阶段）

| 阶段 | 时长 | 主策划 | 客户端程序 | 2D 美术 | 测试运营 | 出口标准 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 立项 | 0.5 天 | 一页纸立项 + 判定口径 | 技术选型与风险 | 风格参考 2–3 套 | 目标平台与合规确认 | 一页纸通过 |
| 1 垂直切片 | 3–5 天 | 关卡 1–3 规格 + 数值表 | A 模式：核心判定 Demo | 风格圣经 + 首屏 UI 线框 | 判定用例 + 兼容初测 | 能玩一关，手感方向明确 |
| 2 内容量产 | 2 周 | 15 关 + 全部模式规则 | A/B 并行：关卡加载 + UI/结算 | 全套切图 + 动效 | 全量用例 + 埋点校验 | 15 关可连贯玩通 |
| 3 打磨 | 1 周 | 难度曲线调优 | 性能/适配/包体 | 资源优化 + 分享素材 | 兼容矩阵 + 回归 | 低端机达帧，无 P0 |
| 4 上线 | 1 周 | 提审资料与文案 | 热更与回滚预案 | 商店图 + 短视频素材 | 提审 → 上线 → 数据监控 | 提审通过 + 首日数据可用 |

**每个迭代必须产出一个「可玩版本」**，不收「纯文档迭代」。

## 三、交接与裁决（这套预设能协作的关键）

### 3.1 交接模板（复制即用）

```
【交接｜谁 → 谁】
目标：这次要达成什么（一句话）
输入：文件路径 / 表格 / 参考图
产出：具体交付物清单（含格式）
约束：不能动什么、性能/包体/工期边界
验收：怎样算做对了（可判定）
截止：日期
```

### 3.2 裁决权（避免吵不出结果）

| 冲突类型 | 拍板人 |
| --- | --- |
| 手感、数值、判定口径、关卡难度 | 主策划 |
| 实现方案、性能、工期、包体 | 客户端程序 |
| 视觉一致性与美术规格 | 2D 美术 |
| 上线风险、合规、提审 | 测试 / 运营 |

拍板结果写进 `docs/决策记录.md`：日期 / 谁 / 结论 / 理由 / 何时复盘。

### 3.3 写作用域（多人/多 Agent 并行时最容易翻车的地方）

- 一个文件同一时间只能有一个 Agent 在改；
- 按目录分工：设计 → `docs/design/`，技术 → `docs/tech/` + `Assets/Scripts/`，美术 → `docs/art/` + `Assets/Art/`，测试 → `docs/qa/`；
- 用 [团队任务看板模板.csv](团队任务看板模板.csv) 管理任务与依赖。

## 五、常见坑

1. **一上来就要成品的完整 GDD**：先要一页纸 + 一关可玩，剩下的按迭代补。
2. **让多个 Agent 同时改同一个文件**：必然冲突；用任务看板和写作用域隔开。
3. **不给验收标准就开工**：AI 会给你「看起来对」但没法验的东西；每条任务都写清「怎样算做对」。
4. **判定口径中途改**：程序、测试、数值全要返工；口径在第一版就锁死并写进文档。
5. **只让策划想点子，不让其他角色反驳**：小团队最大的优势是能快速互相挑错，别浪费。
