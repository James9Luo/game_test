### 12.1 语义（lead 锁定，不选另两种）

**一关按两次，每次定格"当前最接近绿框的那个物体"，两次都合格才算过关。**
❌ 两个同时对准（求交集，错拍后交集可能为 0）；❌ 只判主物体（玩家觉得按准了不算）。

### 12.2 400ms 冻结 = **推后时间轴，不消耗时间轴**（S19 的核心）

```
第一次按下 t1 → phase='frozen'，画面冻在 t1，展示该 mover 的反馈与热力图
400ms 后 → pauseAccum += 400；attemptStart += 400；phase='aim'
```
两个量都必须成立，**缺一不可**（lead 裁定"两个量都断"）：

| 量 | 断言 | 防的失败模式 |
| --- | --- | --- |
| `timerElapsed()` 前后相等 | S19 第一半 | **计时被吃掉**（400ms 反馈计入了倒计时） |
| `attemptStart` 恰 +400 | S19 第二半 | **运动被吃掉**（解冻后物体相位前移了 400ms，第二次窗口被压缩） |

### 12.3 状态机与数据（都归**原型层**，core 保持纯函数）

| 项 | 位置 | 同步关（`phase_2=0`）行为 |
| --- | --- | --- |
| `desyncPhase(def)` / `isDesync()` | `game.js` | 缺省 0 → `isDesync()` false → 所有错拍代码短路 |
| `app.phase` = `'aim' | 'frozen' | 'result'` | `app` / `beginAttempt` / `settle` / `triggerTimeout` | 只有 `aim→result`，无 `frozen` |
| `app.frozen[]`（per-mover 已定格） | `startLevel` 建数组；`beginAttempt` 清 null | 恒 `null`（HUD 点组不画） |
| HUD「还需定格 N 个」+ 空心/实心两点 | `drawDesyncHud()` | **一个像素都不画**（S20） |
| 首次提示「这一关按两次」2s 淡出 | `drawDesyncHint()`（模块级 `desyncHintShown`，本会话仅一次） | 不画 |
| 分次热力图 | `drawHeatmap(res, fade, onlyIndex)`，`fb.moverIndex` 决定只画哪个 | `onlyIndex=null` → 画全部（行为不变） |

**`frozen` 为什么归原型层**：它是"这一关里哪个物体已被定格"的**会话状态**，不是几何。core 保持"无随机、无 UI、无状态机"的纯粹性；S21（失败后全部重置）本来就是这个状态机的职责。

### 12.4 core 的契约（lead 锁定）

```js
judgeNearest(rt, tMs, skipIdx) → { moverIndex, pct, rating, score, timing, objects }
// skipIdx: number[]（调用方告知"哪些 mover 已定格"）
// objects: 只含该 mover 的结果 → 热力图直接吃，无需再筛
// 全部已定格时返回 null（调用方要有防御）
```

### 12.8 三条"测试自证"原则（本轮全部踩过）

| # | 原则 | 踩到的形状 |
| --- | --- | --- |
| 1 | **冻结"推后时间轴"后，所有后续完美时刻都要 + 累计冻结时长；且每次按下都会再冻结一次** | 第二次按下少加 400ms → mover1 窗口只有 ±14~24ms → 把**正确实现**判成失败 |
| 2 | **自测里用 `\|\|` 兜底时间必须在 detail 里打出实际值** | `movers[1].perfectMs` 取不到 → 静默回落成 `t1`，失败原因被伪装成"窗口太窄"；现在 detail 带 `t2Used / perfect0 / perfect1 / worstPct` |
| 3 | **先证明测试场景成立，再断言被测行为** | S21 用"半周期"当故意失败，但 h_line + passRate 0.70 下物体在另一端仍可能 ≥70% → 场景不成立，断言失去意义；最终改用**超时**构造失败（见 12.9），并加 `failIsReal` 自检 |

> 可直接用 `CORE.hitWindowByMover(rt)[i]` 反推第 i 个 mover 的窗口宽度（S18 已由 core 覆盖）。
> 自测驱动 helper：`moverPerfectMs(i)`（给 moverTiming.perfectMs，已含 offset）与 `perfectPressClockMs(i) = attemptStart + perfectMs`（墙钟，已含累计冻结推后）。

### 12.9 "故意失败"必须用产品里确定性的失败路径（lead 2026-10-18 裁定）

> **不能用直觉距离**（半周期、完美点 +200ms 都测到过 ≥ passRate）。

根因：**连续运动的物体在对称路径上，几何重合率与"时间差"不成单调关系**——离完美点很远 ≠ 一定不合格。
所以"故意打偏"永远造不出可靠失败，只能改用**产品里本来就确定性失败的路径**：

| 手段 | 为什么可靠 | 与产品的一致性 |
| --- | --- | --- |
| `triggerTimeout()`（S21 最终采用） | 超时是产品的确定失败分支，任何形状/路径都成立 | 与"任一 mover 不合格"**共用同一条 reset 分支**，测的正是要保的那条逻辑 |

**判据顺序**：测试场景先自证（`failIsReal` / `pass === false`）→ 再断言被测行为（重置 / 扣次）。
否则"永远绿"和"永远红"在日志里看起来一样。
