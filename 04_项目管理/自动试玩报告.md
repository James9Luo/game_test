## 1. 方法与口径（先把「怎么按」说清楚，否则数字没意义）

| 项 | 取值 |
|---|---|
| 浏览器 | Edge `Edg/142.0.3595.53`，`--headless=new`，独立临时 profile |

| 入口 | **`?start=N`**（v0.9.1 真试玩，时钟正常走），每关一个全新页面 |

### 1.1 为什么不用 `?screen=play&lvl=N`（任务书里写的那个入口）

`?screen=play` 命中的是 `applyDebug()` 的**截图分支**：它把 `timeFreeze` 钉在 `cycleMs × frac` 上，
时钟从此不走。实测（`_results_diag.json` → `preflight.screenPlay`）：

| 观测 | 实测值 | 含义 |
|---|---|---|
| 450 ms 前后 `__PROTO__.now()` | `1779.2500000000002` → `1779.2500000000002` | **时钟完全不动** |
| 冻结状态下真点一下 | 被判：`tier=ok`、`pct=54.3` | 会出结算，但… |
| 那一次的「按下时刻」 | `1779.25` = 冻结帧 | **什么时候点，都判在这一帧** |

结论：`?screen=play` 只能用来截图/看构图，**不能用来玩**（物体不动，"按早了/按晚了"根本无从产生）。
真试玩入口是 `?start=N`（`startRun()` + `timeFreeze = null`）。本工具全程用 `?start=N`。

### 1.2 点击精度是怎么做到 ms 级的（也是本轮唯一一次踩坑）

headless 下 rAF 只有 **26.7 – 33.1 fps**（`preflight.fps`），一帧 30–40 ms、偶尔 100 ms+。
只靠 Node 端掐表 + `Input.dispatchMouseEvent`，点击会被这一帧挡在门外：**工具第一版实测系统偏差 +17…+107 ms**（见 §5）。

现在的做法是**页面自旋屏障**：提前 150 ms 让页面自己 `while(performance.now()<目标){}` 自旋，
再在目标前 40 ms 把点击发过去 —— 点击到达时主线程正卡在自旋里，排在该 task 之后，
自旋结束（= 页面时钟到点）立刻被处理。于是「按下时刻」由**页面时钟**决定，与 Node 抖动无关。
误差实测 0.1 ms（p95 0.4 ms）。工具会自适应：某次 \|Δ\|>12 ms 就自动加宽屏障。

## 3. 待修清单

> 判定层：**0 条**。下面 4 条全在入口 / 调试开关 / 观感层，按严重度排。

### P1 · 交给人类试玩的入口用的是「冻结截图」URL，物体根本不动

| 项 | 内容 |
|---|---|
| 现象 | `原型/试玩入口_v11.html` 里 iframe 与 10 个关卡 chip 拼的都是 `dista_prototype.html?screen=play&lvl=N` |
| 证据 | 该分支把 `timeFreeze` 钉死：450 ms 内 `now()` 两个值完全相同（`1779.2500000000002`）；此时点击仍会结算，但按下时刻恒等于冻结帧 `1779.25` ⇒ 点什么、什么时候点都是同一帧（`preflight.screenPlay`） |
| 影响 | 试玩者看到的是**一张静图**，"等太久 / 刚好 / 太赶"这类节奏反馈**测不出来**；D-128 修复记录里"第一下点击被吃掉"的现象也是在这个入口下被观察到的，而它根本不是可玩状态 |
| 建议 | 入口页改成 `?start=N`（真试玩，v0.9.1 已有）：`frame.src='dista_prototype.html?start='+lvl`；`?screen=play` 只留在截图脚本里 |
| 验收 | 打开入口页 → 物体在飞；连续两次读 `__PROTO__.now()`（间隔 450 ms）差值 ≥ 400 ms |
| 状态 | 未修（我不改别人的文件） |

### P2 · 直链进关后的第一下点击被吞（D-128 设计内，但外部试玩者会遇到）

| 项 | 内容 |
|---|---|
| 现象 | 通过 `?start=N` 进关后，第一次点击只解锁音频，**不判定** |
| 证据 | 本轮 60/60 关的第一下点击全部"未判"（`warmupSwallowed: 60`）；代码位置 `handlePressAt` 里 `_firstGesture = _unlocked && !app.audioGestureDone` → `if (_firstGesture) return;` |
| 影响 | 从分享链接 / 试玩入口直接进关的玩家，第一下"按上了"的操作没有反馈（错拍关会白丢一次定格机会）；从首页点进去的玩家不受影响（首页那下已解锁） |
| 建议 | 判定口径不动。两个选项：(a) 试玩说明里加一句"第一下点击先解锁声音"；(b) 对 `?start=` 直链路径先放一个"轻点开始"的全屏提示，把这次点击显式化。**改判定前先跑 `modes_check` 的 D-128 断言**，别直接删 |
| 验收 | `?start=1` 进关 → 第一下点击后 `app.scene` 仍为 `play` 且 `app.fb === null`（现状）；改后应为点击即判 |
| 状态 | 设计如此，待产品决策 |

### P2 · `?autoplay=1&press=0.5` 是死开关（一次都没按）

| 项 | 内容 |
|---|---|
| 现象 | 加载 `?autoplay=1&press=0.5&lvl=1` 等 2.2 s：`scene=home`、`pressGlow=-1000000000`、`fb=null` |
| 原因 | `applyDebug()` 在无 `?screen=` 时走首页开场（`scene='home'`），而定时器里的兜底是 `if (app.scene === 'play') doPress(...)` ⇒ 永远不成立 |
| 影响 | 任何"用它验证判定链是否正常"的脚本都会得到假绿灯；任务书里"`&press=0.5` 是自动按一次"的说法与实现不符（`press` 只是 `?screen=play` 的冻结相位） |
| 建议 | 删掉该死分支，或改成 `startRun('challenge', N-1)` 后再定时 `doPress` |
| 验收 | `?autoplay=1` 加载 2 s 内 `app.fb` 应非空；现状为 null |
| 状态 | 未修（调试代码，低优先） |

### P3 · 每季首关的「第 N 季」字卡压住第一圈（首个完美窗口在字卡里）

| 项 | 内容 |
|---|---|

| 状态 | 待复核（观感/时序，不是 bug） |

### P3 · 已定格物体压暗 0.32，浅色道具几乎只剩绿框

| 项 | 内容 |
|---|---|
| 现象 | 错拍关结算时两个物体都在 `globalAlpha = alpha * 0.32`（D-128「已定格压暗」）；L50 的马克杯、L60 的拖鞋在深色背景上几乎只看得见绿框 |
